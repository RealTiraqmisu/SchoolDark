# คำอธิบายฐานข้อมูลรายหมวด (ฉบับร่างสำหรับเล่มรายงาน)

เอกสารนี้อธิบายฐานข้อมูลของระบบทีละหมวด โดยเริ่มจากภาพรวมว่าข้อมูลเดินทางข้ามหมวดอย่างไร แล้วจึงลงรายละเอียดทีละหมวด ชื่อตารางทุกชื่อตรงกับรูป ER A4 ในเล่มและไฟล์ `erd-types.md` เครื่องหมาย ❓ คือจุดที่แหล่งข้อมูลไม่ได้ยืนยัน ผู้เขียนควรตรวจก่อนลงเล่ม

---

## บทนำภาพรวม

ฐานข้อมูลของระบบมีตารางราว 60 ตาราง ถ้าอ่านทีละตารางจะเห็นแต่รายการคอลัมน์ ไม่เห็นว่าข้อมูลมาจากไหนและไปไหน ส่วนนี้จึงเล่าเป็นเรื่องเดียวตาม DFD Level 1 ซึ่งแบ่งระบบเป็น 4 กลุ่มใหญ่ ได้แก่ ตั้งค่าโรงเรียน รับสมัคร ทะเบียนนักเรียน และบุคลากร (รวมตั้งค่าบุคลากร) แต่ละกลุ่มแสดงเฉพาะตารางหลัก ส่วนตารางย่อยที่เหลือจะอธิบายในหมวดของตัวเอง

เรื่องเริ่มจากการตั้งค่าโรงเรียน ตาราง AcademicYears เก็บปีการศึกษาและ StudyProgram เก็บแผนการเรียนที่โรงเรียนเปิดสอน เมื่อโรงเรียนจะรับนักเรียนใหม่ เจ้าหน้าที่เปิดรอบรับสมัครขึ้นในปีการศึกษานั้น โดยสร้าง AdmissionRound แล้วกำหนดว่ารอบนี้รับแผนการเรียนใดบ้างด้วย AdmissionCoursePlan นี่คือกระบวนการ 1.0 "เปิดรอบรับสมัคร" เมื่อรอบเปิดแล้ว ผู้สมัครกรอกและยื่นใบสมัคร ระบบบันทึกเป็นแถวใหม่ในตาราง Application ภายใต้รอบนั้น นี่คือกระบวนการ 2.0 "ผู้สมัครยื่นใบสมัคร"

ผู้สมัครที่ได้รับคัดเลือกและมาทำการมอบตัวจะกลายเป็นนักเรียน ตอนนี้ระบบสร้างแถวใหม่ในตาราง Student แล้วคัดลอกข้อมูลจากใบสมัครมาไว้ โดยเก็บว่าคัดลอกมาจากใบไหนไว้ที่คอลัมน์ `fromApplicationID` นี่คือกระบวนการ 3.0 "มอบตัว · คัดลอกข้อมูล" ลูกศรเส้นนี้เป็นการคัดลอก ไม่ใช่การอ้างอิง หลังมอบตัวข้อมูลของนักเรียนกับข้อมูลในใบสมัครเป็นคนละชุด แก้อันหนึ่งไม่กระทบอีกอัน ในภาพจึงวาดต่างจากลูกศรอื่นที่เป็นการอ้างอิงด้วยคีย์ปกติ

ฝั่งห้องเรียน เมื่อเริ่มปีการศึกษา โรงเรียนสร้างห้องเรียนรายปีในตาราง Classroom จากปีการศึกษาและระดับชั้น (ตาราง EducationLevels) นี่คือกระบวนการ 4.0 "สร้างห้องเรียนรายปี" จากนั้นนักเรียนถูกจัดเข้าห้อง โดยบันทึกในตาราง StudentClassHistory ว่านักเรียนคนไหนอยู่ห้องไหน และเมื่อขึ้นปีใหม่ก็เพิ่มแถวใหม่เพื่อเลื่อนชั้น นี่คือกระบวนการ 5.0 "จัดห้อง / เลื่อนชั้น" ถ้านักเรียนลาออก จบ หรือย้ายสถานศึกษา ระบบบันทึกการเปลี่ยนสถานะลงตาราง StudentStatusHistory นี่คือกระบวนการ 6.0 "ลาออก / จบ / ย้าย"

ปลายทางสุดท้ายคือครูและบัญชีผู้ใช้ ตาราง Employees เก็บข้อมูลบุคลากร ห้องเรียนหนึ่งห้องมีครูประจำชั้นได้หลายคน จึงใช้ตาราง ClassroomHomeroomTeacher เชื่อมระหว่างห้องกับบุคลากร และบุคลากรที่ต้องเข้าใช้ระบบจะมีบัญชีในตาราง User นี่คือกระบวนการ 7.0 "กำหนดครูประจำชั้น" และ "บัญชีเข้าระบบ" ส่วนที่เกี่ยวกับบุคลากรทั้งหมดยังไม่ผ่านการยืนยันโครงสร้างระบบจากเจ้าของข้อมูล ❓

สรุปทิศทางของข้อมูลคือ ไหลจากตั้งค่าไปรับสมัคร จากรับสมัครไปทะเบียนนักเรียนโดยการคัดลอกที่จุดมอบตัวจุดเดียว และจากบุคลากรมาเชื่อมกับห้องเรียนที่ฝั่งทะเบียน หมวดถัดไปอธิบายแต่ละกลุ่มตามลำดับนี้

---

## วิธีการทำงานของระบบ (กระบวนการ 1.0–7.0)

ส่วนนี้สรุปกระบวนการทั้ง 7 ใน DFD Level 1 แบบสั้น ชื่อกระบวนการและเลข D ตรงกับแผนภาพ ได้แก่ D1 AcademicYears, D2 EducationLevels, D3 StudyProgram, D4 AdmissionRound, D5 AdmissionCoursePlan, D6 Application, D7 Student, D8 Classroom, D9 StudentClassHistory, D10 StudentStatusHistory, D11 ClassroomHomeroomTeacher, D12 Employees, D13 User ผู้ทำตรวจกับ use case diagram แท็บ "เล่มรายงาน (A4) รวม actor" ส่วนขั้นตอนอ้างจากคำอธิบาย use case (UC-xxx) และแหล่งข้อมูลเดิม

### 1.0 ตั้งค่าปีการศึกษาและเปิดรอบรับสมัคร

- **ผู้ทำ:** ผู้ดูแลระบบ (ปีการศึกษา ระดับชั้น) และหัวหน้างานทะเบียน (รอบรับสมัคร แผนที่เปิดรับ) · ผู้ตั้งค่า StudyProgram ❓ (use case ไม่ระบุ)
- **ข้อมูลเข้า:** ปีการศึกษา ระดับชั้นที่เปิดใช้ แผนการเรียน กำหนดการของรอบ จำนวนที่รับ ระเบียบ ค่าสมัครของแต่ละแผน
- **ขั้นตอน:**
  1. ผู้ดูแลระบบกำหนดปีการศึกษา ภาคเรียน ระดับชั้นที่เปิดใช้ และระดับชั้นถัดไปของแต่ละระดับชั้น (UC-SET-01)
  2. หัวหน้างานทะเบียนสร้างรอบรับสมัครของปีการศึกษานั้น ระบุช่วงวันและเปิดใช้งานรอบ (UC-SET-04)
  3. หัวหน้างานทะเบียนเลือกแผนการเรียนที่เปิดรับในรอบ พร้อมจำนวนที่รับ ระเบียบ และค่าสมัคร (UC-SET-04)
  4. ระบบตรวจว่ามีฟิลด์บังคับครบ ช่วงวันถูกต้อง และมีแผนที่เปิดรับอย่างน้อยหนึ่งแผน แล้วบันทึก
- **ตารางที่อ่าน / เขียน:** อ่าน — · เขียน D1 AcademicYears, D2 EducationLevels, D3 StudyProgram, D4 AdmissionRound, D5 AdmissionCoursePlan
- **ผลลัพธ์:** รอบและแผนที่เปิดรับส่งต่อให้ 2.0 ปีการศึกษาและระดับชั้นส่งต่อให้ 4.0
- **เหตุผลการออกแบบ:** ปีการศึกษาและระดับชั้นเก็บส่วนกลางครั้งเดียว ใช้ร่วมสองฝั่ง ดูหมวดตั้งค่าโรงเรียนและตารางอ้างอิงกลาง

### 2.0 รับและพิจารณาใบสมัคร

- **ผู้ทำ:** ผู้สมัครเรียน (ยื่นใบสมัคร) และเจ้าหน้าที่งานทะเบียน (ตรวจเอกสาร จัดการสถานะ)
- **ข้อมูลเข้า:** ข้อมูลส่วนตัว ที่อยู่ ผู้ปกครอง การศึกษาเดิม สุขภาพ เอกสารแนบ รอบและแผนที่เลือก
- **ขั้นตอน:**
  1. ผู้สมัครเลือกรอบและแผน กรอกแบบฟอร์มเป็นขั้น และอัปโหลดเอกสาร (UC-ADM-06)
  2. ผู้สมัครยืนยันตัวด้วย OTP ที่ส่งไปอีเมลผู้ติดต่อหลัก แล้วส่งใบสมัคร ระบบบันทึกเป็นใบสมัครใบใหม่เสมอ
  3. เจ้าหน้าที่งานทะเบียนตรวจเอกสารแต่ละรายการ บันทึกว่าครบหรือไม่ครบ (UC-ADM-02)
  4. เจ้าหน้าที่งานทะเบียนปรับสถานะใบสมัคร ระบบเก็บประวัติการเปลี่ยนสถานะ (UC-ADM-03)
- **ตารางที่อ่าน / เขียน:** อ่าน D4 AdmissionRound, D5 AdmissionCoursePlan · เขียน D6 Application (รวมตารางย่อย 5 ตาราง คือ ApplicantAddress, ApplicantGuardian, ApplicantHealth, ApplicationDocument, ApplicationStatusHistory)
- **ผลลัพธ์:** ผลการสมัครและอีเมลแจ้งผู้สมัครเรียน ส่วนใบสมัครของผู้ที่ได้รับคัดเลือกส่งต่อให้ 3.0
- **เหตุผลการออกแบบ:** ใบสมัครเป็น log ของวันที่ยื่น ไม่ผูกตารางบุคคลกลาง ดูหมวดรับสมัคร · ADR 0001

### 3.0 มอบตัวเป็นนักเรียน

- **ผู้ทำ:** เจ้าหน้าที่งานทะเบียน
- **ข้อมูลเข้า:** ใบสมัครของผู้ที่ได้รับคัดเลือก
- **ขั้นตอน:**
  1. เจ้าหน้าที่งานทะเบียนเลือกใบสมัครที่มอบตัว ❓ (use case description ไม่มีขั้นนี้ มีแต่ขั้นเพิ่มนักเรียนใหม่ UC-REG-01)
  2. ระบบหา Student เดิมด้วยเลขบัตรประชาชน ถ้าเจอใช้แถวเดิม ถ้าไม่เจอสร้างแถวใหม่ (ADR 0001)
  3. ระบบคัดลอกตัวบุคคล ที่อยู่ สุขภาพ ผู้ปกครอง การศึกษาเดิม และเอกสาร ไปเป็นชุดข้อมูลของนักเรียน และเก็บใบสมัครต้นทางที่ `fromApplicationID`
  4. ระบบออกรหัสนักเรียนและตั้งสถานะ "กำลังศึกษา" ตามขั้นเพิ่มนักเรียนใหม่ (UC-REG-01) ❓ ยังไม่ระบุว่าการมอบตัวใช้ขั้นเดียวกันหรือไม่
- **ตารางที่อ่าน / เขียน:** อ่าน D6 Application · เขียน D7 Student (รวมตารางย่อย 5 ตาราง คือ StudentAddress, StudentHealth, StudentGuardian, StudentDocument, StudentStatusHistory)
- **ผลลัพธ์:** แถวนักเรียนส่งต่อให้ 5.0 และ 6.0
- **เหตุผลการออกแบบ:** เป็นการคัดลอก ไม่ใช่การอ้างอิง แก้ข้อมูลนักเรียนได้โดยไม่กระทบใบสมัคร ดูหมวดทะเบียนนักเรียน · ADR 0001 และ 0002

### 4.0 สร้างห้องเรียนรายปี

- **ผู้ทำ:** หัวหน้างานทะเบียน ❓ (use case "ตั้งค่างานทะเบียนนักเรียน" UC-SET-03 ระบุแค่รูปแบบรหัสนักเรียนและคอลัมน์ในรายการ ไม่มีการสร้างห้องเรียน)
- **ข้อมูลเข้า:** ปีการศึกษา ระดับชั้น เลขห้อง แผนการเรียน ความจุ ห้องจริง (ไม่บังคับ)
- **ขั้นตอน:**
  1. ผู้ทำเลือกปีการศึกษาและระดับชั้นของห้อง ❓ (use case description ไม่มีขั้นตอนหน้าจอของกระบวนการนี้)
  2. ระบุเลขห้อง แผนการเรียน ความจุ และห้องจริงของอาคาร (ไม่บังคับ)
  3. ระบบบันทึกห้อง โดยกฎคือช่วงชั้นของระดับชั้นต้องตรงกับช่วงชั้นของแผนการเรียน (erd-spec §2.6, §8.2)
- **ตารางที่อ่าน / เขียน:** อ่าน D1 AcademicYears, D2 EducationLevels · เขียน D8 Classroom
- **ผลลัพธ์:** ห้องเรียนรายปีส่งต่อให้ 5.0 และ 7.0
- **เหตุผลการออกแบบ:** ห้องเรียนคือกลุ่มนักเรียนของปีหนึ่ง ไม่ใช่ห้องจริงของอาคาร ดูหมวดทะเบียนนักเรียน

### 5.0 จัดห้องและเลื่อนชั้น

- **ผู้ทำ:** เจ้าหน้าที่งานทะเบียน
- **ข้อมูลเข้า:** รายชื่อนักเรียนสถานะ "กำลังศึกษา" ห้องปลายทาง เลขที่
- **ขั้นตอน:**
  1. เจ้าหน้าที่งานทะเบียนเลือกคำสั่งเลื่อนชั้นและบันทึกการสำเร็จการศึกษา (UC-REG-04)
  2. ระบบดึงนักเรียนที่กำลังศึกษามาเป็นรายการตั้งต้น เลื่อนชั้นโดยปริยาย เจ้าหน้าที่ยกเว้นผู้ที่ไม่ผ่านเกณฑ์
  3. เจ้าหน้าที่ตรวจสรุปจำนวนที่เลื่อนชั้น จบ และถูกยกเว้น แล้วยืนยัน
  4. ระบบปิดแถวห้องเดิมด้วยวันสิ้นสุด เพิ่มแถวห้องใหม่ของระดับชั้นถัดไป ผู้ไม่มีระดับชั้นถัดไปถือว่าจบ
- **ตารางที่อ่าน / เขียน:** อ่าน D7 Student, D8 Classroom · เขียน D9 StudentClassHistory
- **ผลลัพธ์:** ผลการจัดห้องแจ้งกลับเจ้าหน้าที่งานทะเบียน
- **เหตุผลการออกแบบ:** ห้องเป็นประวัติ ห้องปัจจุบันคือแถวที่ยังไม่มีวันสิ้นสุด ดูหมวดทะเบียนนักเรียน

### 6.0 เปลี่ยนสถานะนักเรียน (ลาออก/จบ/ย้าย)

- **ผู้ทำ:** เจ้าหน้าที่งานทะเบียน
- **ข้อมูลเข้า:** นักเรียนที่เลือก ประเภทการจำหน่ายออก สถานศึกษาปลายทาง เหตุผล วันที่มีผล
- **ขั้นตอน:**
  1. เจ้าหน้าที่งานทะเบียนเลือกนักเรียนและคำสั่งย้ายออก ลาออก หรือพ้นสภาพ (UC-REG-05)
  2. ระบุประเภท (ย้ายไปสถานศึกษาอื่น ลาออก พักการเรียน พ้นสภาพ) สถานศึกษาปลายทาง และเหตุผล
  3. ตรวจสรุปการเปลี่ยนแปลงแล้วยืนยัน
  4. ระบบบันทึกสถานะใหม่ที่นักเรียน และเพิ่มแถวใน StudentStatusHistory (การจบเกิดจากขั้นเลื่อนชั้นใน 5.0)
- **ตารางที่อ่าน / เขียน:** อ่าน D7 Student · เขียน D10 StudentStatusHistory, D7 Student (สถานะ)
- **ผลลัพธ์:** ผลการเปลี่ยนสถานะแจ้งกลับเจ้าหน้าที่งานทะเบียน
- **เหตุผลการออกแบบ:** เก็บประวัติสถานะเพื่อย้อนกลับรายการได้ ดูหมวดทะเบียนนักเรียน

### 7.0 จัดการบุคลากร ครูประจำชั้น และบัญชีผู้ใช้

- **ผู้ทำ:** เจ้าหน้าที่งานบุคคล (ข้อมูลบุคลากร) และผู้ดูแลระบบ (บัญชีและสิทธิ์) ❓ ใครกำหนดครูประจำชั้น
- **ข้อมูลเข้า:** ข้อมูลพื้นฐาน การศึกษา ตำแหน่งงานของบุคลากร ห้องเรียนที่ต้องมีครูประจำชั้น (โครงสร้างฝั่งบุคลากรยังไม่ยืนยัน ❓)
- **ขั้นตอน:**
  1. เจ้าหน้าที่งานบุคคลเพิ่มบุคลากร กรอกข้อมูลพื้นฐาน การศึกษา ตำแหน่งงาน แล้วบันทึก (UC-STF-02)
  2. เลือกบุคลากรเป็นครูประจำชั้นของห้องในปีการศึกษานั้น ระบบเพิ่มแถวใน ClassroomHomeroomTeacher ❓ (use case ไม่มีขั้นตอนนี้)
  3. สร้างบัญชีให้บุคลากร 1 คน 1 บัญชี กำหนด `accessRole` ❓ (use case ไม่มีขั้นตอนสร้างบัญชี)
- **ตารางที่อ่าน / เขียน:** อ่าน D8 Classroom, D12 Employees · เขียน D12 Employees, D11 ClassroomHomeroomTeacher, D13 User
- **ผลลัพธ์:** ครูประจำชั้นของห้อง (ให้ฝั่งทะเบียนนักเรียน) และบัญชีเข้าระบบของบุคลากร
- **เหตุผลการออกแบบ:** ห้องหนึ่งมีครูประจำชั้นได้หลายคนจึงใช้ตารางคั่น ดูหมวดทะเบียนนักเรียน หมวดบุคลากร และหมวดตั้งค่าบุคลากร

## หมวดรับสมัคร

หมวดนี้เก็บทุกอย่างตั้งแต่โรงเรียนเปิดรอบรับสมัครจนถึงผลของใบสมัครแต่ละใบ ใช้ให้เจ้าหน้าที่จัดการรอบและแผนที่เปิดรับ ใช้ให้ผู้สมัครกรอกข้อมูล และใช้ติดตามว่าใบสมัครแต่ละใบอยู่ในสถานะใด ตั้งแต่ยื่น ตรวจเอกสาร ไปจนถึงผลการคัดเลือก

### ตารางในหมวดนี้ (ภาพรวมก่อนดูรูป ER)

| ชื่อตาราง | รายละเอียดตาราง |
|---|---|
| AdmissionRound | รอบรับสมัครของปีการศึกษา ปีหนึ่งมีได้หลายรอบ และเก็บกำหนดการทั้ง 6 วันของรอบ |
| AdmissionCoursePlan | แผนการเรียนที่เปิดรับในแต่ละรอบ เก็บจำนวนที่รับ ระเบียบ และค่าสมัคร |
| Application | ใบสมัครแต่ละใบ เป็น log ข้อมูล ณ วันยื่น ติดตามสถานะ |
| ApplicantAddress | ที่อยู่ผู้สมัคร ตามทะเบียนบ้านและปัจจุบัน |
| ApplicantGuardian | บิดา มารดา ผู้ปกครองของผู้สมัคร และช่องทางติดต่อ |
| ApplicantHealth | ข้อมูลสุขภาพของผู้สมัคร 1 แถวต่อใบสมัคร |
| ApplicationDocument | เอกสารแนบใบสมัครและผลตรวจของเจ้าหน้าที่ |
| ApplicationStatusHistory | ประวัติการเปลี่ยนสถานะของใบสมัคร ใช้ย้อนกลับรายการ |

ตารางจากหมวดอื่นที่เกี่ยวข้อง (ปรากฏเป็นกล่องเทาในรูป ER A4 · รับสมัคร)

| ชื่อตาราง | หมวดเจ้าของ | เกี่ยวข้องกับหมวดนี้อย่างไร |
|---|---|---|
| Student | ทะเบียนนักเรียน | Student ชี้มาที่ Application ผ่าน `fromApplicationID` เพื่อบอกว่านักเรียนคัดลอกข้อมูลจากใบสมัครใบไหน |
| StudyProgram | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | AdmissionCoursePlan ชี้ไปที่ StudyProgram ผ่าน `studyProgramID` เพื่อบอกว่าแผนที่เปิดรับคือแผนการเรียนใด |
| SubDistricts | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | ApplicantAddress ชี้ไปที่ SubDistricts ผ่าน `subDistrictID` เพื่อบอกตำบลของที่อยู่ผู้สมัคร |
| AcademicYears | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | AdmissionRound ชี้ไปที่ AcademicYears ผ่าน `academicYearID` เพื่อบอกว่ารอบนี้อยู่ในปีการศึกษาใด |
| FieldDefinition | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | ApplicationDocument ชี้ไปที่ FieldDefinition ผ่าน `fieldID` เพื่อบอกชนิดของเอกสารแต่ละไฟล์ |

#### ผังตารางหลักและตารางย่อย

อ่านผังนี้ได้ดังนี้ ตารางที่มี [หลัก] คือตารางหลัก ส่วนตารางที่เยื้องอยู่ใต้คือตารางย่อยที่มี FK ชี้ไปตารางด้านบน

```
AdmissionRound                           [หลัก]
└─ AdmissionCoursePlan                   [หลัก]   (roundID)
   └─ Application                        [หลัก]   (planID) → ชี้ไป AdmissionRound ด้วย (roundID)
      ├─ ApplicantAddress                         (applicationID)
      ├─ ApplicantGuardian                        (applicationID)
      ├─ ApplicantHealth                          (applicationID)
      ├─ ApplicationDocument                      (applicationID)
      └─ ApplicationStatusHistory                 (applicationID)
```

อ้างอิงตารางจากหมวดอื่น: AcademicYears (หมวดตั้งค่าโรงเรียนฯ) เป็นแม่ของ AdmissionRound, StudyProgram (หมวดตั้งค่าโรงเรียนฯ) เป็นแม่ของ AdmissionCoursePlan, SubDistricts (หมวดตั้งค่าโรงเรียนฯ) เป็นแม่ของ ApplicantAddress, FieldDefinition (หมวดตั้งค่าโรงเรียนฯ) เป็นแม่ของ ApplicationDocument, และ Student (หมวดทะเบียนนักเรียน) เป็นตารางย่อยของ Application ผ่าน `fromApplicationID`

ตารางหลักมี 3 ตาราง AdmissionRound คือรอบรับสมัครของปีการศึกษาหนึ่ง ปีหนึ่งมีได้หลายรอบ เช่น รอบห้องพิเศษและรอบห้องธรรมดา และเก็บกำหนดการทั้ง 6 วัน ได้แก่ วันเปิดรับ ปิดรับ สอบ ประกาศผล รายงานตัว และมอบตัว AdmissionCoursePlan คือแผนการเรียนที่เปิดรับในรอบนั้น เก็บจำนวนที่รับ ระเบียบการ และค่าสมัครของแต่ละแผน ส่วน Application คือใบสมัครหนึ่งใบ เก็บข้อมูลผู้สมัครทั้งหมดตามที่กรอก ณ วันที่ยื่น ตารางที่เหลืออีก 5 ตารางเป็นตารางย่อยของใบสมัคร ได้แก่ ApplicantAddress (ที่อยู่ตามทะเบียนบ้านและปัจจุบัน) ApplicantGuardian (บิดา มารดา ผู้ปกครอง และช่องทางติดต่อ) ApplicantHealth (สุขภาพ 1 แถวต่อใบสมัคร) ApplicationDocument (เอกสารแนบและผลตรวจของเจ้าหน้าที่) และ ApplicationStatusHistory (ประวัติการเปลี่ยนสถานะ ใช้ย้อนกลับรายการได้) ทุกตารางย่อยชี้กลับมาที่ Application ด้วย `applicationID`

ข้อมูลไหลตามภาพดังนี้ รอบเกิดจากปีการศึกษาและแผนการเรียนที่ตั้งไว้ในหมวดตั้งค่า (กระบวนการ 1.0) ผู้สมัครแต่ละคนยื่นใบสมัครเข้ามาในรอบ (กระบวนการ 2.0) และเมื่อผู้สมัครได้รับการคัดเลือกและมอบตัว ข้อมูลของใบสมัครถูกคัดลอกไปที่ตาราง Student ของหมวดทะเบียนนักเรียน (กระบวนการ 3.0) นอกจากนี้ ApplicationDocument ชี้ไปที่ FieldDefinition เพื่อบอกว่าเอกสารแต่ละไฟล์เป็นชนิดใด

เหตุผลการออกแบบข้อสำคัญคือให้ใบสมัครเป็นบันทึก (log) ของวันที่ยื่นเท่านั้น ไม่เชื่อมกับตารางบุคคลกลาง อาจารย์เสนอให้ย้ายประวัติผู้สมัครไปไว้ที่ตารางบุคคลกลางเพื่อให้ผู้สมัครคนเดิมใช้ข้อมูลเดิมได้ แต่ทีมเลือกไม่ทำตามนั้น เพราะถ้ามีข้อมูลกลาง การสมัครรอบใหม่จะทับข้อมูลของใบเก่า ตัวอย่างเช่น ผู้สมัครที่สมัคร ม.1 ปี 2569 ด้วย GPAX 3.20 แล้วกลับมาสมัคร ม.4 ปี 2572 ด้วย GPAX 3.80 ใบปี 2569 จะกลายเป็น 3.80 ซึ่งผิดจากความจริงของใบนั้น การเป็น log ทำให้ใบเก่าคงเดิมโดยไม่ต้องสร้างกลไกเก็บประวัติเพิ่ม และเพื่อไม่ให้ผู้สมัครซ้ำต้องกรอกใหม่ ระบบให้ยืนยันตัวด้วยเลขบัตรประชาชนกับ OTP ทางอีเมลของผู้ติดต่อหลัก แล้วดึงใบล่าสุดมาเติมให้ ใบใหม่ยังเป็นใบแยก (ADR 0001) ผลที่ตามมาคือข้อมูลของผู้สมัครคนเดียวอาจซ้ำกันในหลายใบ ซึ่งยอมรับได้เพราะเป็นบันทึกประวัติ และคอลัมน์ `citizenID` ในใบสมัครไม่เป็น UK คีย์ที่ห้ามซ้ำ ส่วนคอลัมน์ `extraFields` (JSONB) น่าจะเก็บคำตอบของช่องกรอกที่โรงเรียนเพิ่มเอง ❓ แหล่งข้อมูลระบุเพียงว่าช่องที่ตั้งค่าผ่าน FieldDefinition เก็บคำตอบไว้ในคอลัมน์ของ Application ตาม `fieldKey`

ดูรูป ER A4 · รับสมัคร (1/2) และ (2/2) และพจนานุกรมข้อมูลของตารางในหมวดรับสมัคร

## หมวดทะเบียนนักเรียน

หมวดนี้เก็บข้อมูลของคนที่มอบตัวแล้ว ได้แก่ ข้อมูลตัวบุคคล สถานะการเป็นนักเรียน ห้องเรียนที่อยู่ในแต่ละปี และครูประจำชั้นของห้อง ใช้ให้เจ้าหน้าที่ทะเบียนจัดห้อง เลื่อนชั้น และบันทึกการจำหน่ายออก

### ตารางในหมวดนี้ (ภาพรวมก่อนดูรูป ER)

| ชื่อตาราง | รายละเอียดตาราง |
|---|---|
| Student | นักเรียนที่มอบตัวแล้ว เก็บข้อมูลตัวบุคคล สถานะ และการจำหน่ายออก |
| StudentAddress | ที่อยู่ของนักเรียน คัดลอกจากใบสมัครตอนมอบตัว |
| StudentHealth | ข้อมูลสุขภาพของนักเรียน คัดลอกจากใบสมัครตอนมอบตัว |
| StudentGuardian | ผู้ปกครองของนักเรียน คัดลอกจากใบสมัคร ไม่มีตารางคั่น |
| StudentDocument | เอกสารของนักเรียน คัดลอกจากเอกสารใบสมัครตอนมอบตัว |
| StudentStatusHistory | ประวัติการเปลี่ยนสถานะของนักเรียน ใช้ย้อนกลับรายการ |
| StudentClassHistory | ประวัติห้องของนักเรียน เก็บวันเริ่ม วันสิ้นสุด และเลขที่ |
| Classroom | ห้องเรียนต่อปีการศึกษา ระดับชั้น และเลขห้อง |
| ClassroomHomeroomTeacher | ครูประจำชั้นของห้อง ห้องหนึ่งมีได้หลายคน ครูหนึ่งคนประจำ 1 ห้องต่อปี |

ตารางจากหมวดอื่นที่หมวดนี้ใช้ (ปรากฏเป็นกล่องเทาในรูป ER A4 · ทะเบียนนักเรียน)

| ชื่อตาราง | หมวดเจ้าของ | หมวดทะเบียนใช้ทำอะไร |
|---|---|---|
| Application | รับสมัคร | เป็นต้นทางที่คัดลอกข้อมูลตอนมอบตัว ชี้โดย `fromApplicationID` ใน Student |
| AcademicYears | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | บอกปีของห้องเรียนและปีที่ครูประจำชั้น |
| EducationLevels | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | บอกระดับชั้นของห้องเรียน |
| StudyProgram | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | บอกแผนการเรียนของห้องเรียน |
| SchoolRoom | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | บอกห้องจริงของห้องเรียน (ไม่บังคับกรอก) |
| SubDistricts | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | บอกตำบลของที่อยู่นักเรียน |
| FieldDefinition | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | บอกชนิดเอกสารของเอกสารนักเรียน |
| Employees | บุคลากร | ให้เลือกบุคลากรเป็นครูประจำชั้น |
| StudentColumnSetting | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | ตั้งว่าหน้ารายชื่อนักเรียนโชว์คอลัมน์ไหน (ไม่อยู่ในรูป ER ทะเบียน) |

การตั้งค่าของงานทะเบียน (StudentColumnSetting และ FieldDefinition) อยู่ในหมวดตั้งค่าโรงเรียนและตารางอ้างอิงกลาง ไม่ได้อยู่ในหมวดทะเบียนนักเรียน

ตารางหลักมี 3 ตาราง Student คือนักเรียนที่มอบตัวแล้ว เก็บชื่อ วันเกิด เลขบัตรประชาชน (ห้ามซ้ำ) สถานะ และวันที่เข้า-จบ รวมถึงคอลัมน์ `fromApplicationID` ที่บอกว่าคัดลอกมาจากใบสมัครใบใด Classroom คือห้องเรียนต่อหนึ่งปีการศึกษา ระดับชั้น และเลขห้อง ไม่ใช่ตัวห้องจริงของอาคาร (ห้องจริงคือ SchoolRoom ในหมวดตั้งค่า) และ StudentClassHistory คือประวัติห้องของนักเรียน เก็บห้อง เลขที่ วันเริ่ม และวันสิ้นสุด ห้องปัจจุบันคือแถวที่ยังไม่มีวันสิ้นสุด ตารางที่เหลือแบ่งเป็น 2 กลุ่ม กลุ่มแรกเป็นตารางย่อยของนักเรียน 5 ตาราง คือ StudentAddress StudentHealth StudentGuardian StudentDocument และ StudentStatusHistory (ประวัติการเปลี่ยนสถานะ ใช้ย้อนกลับรายการได้) กลุ่มที่สอง คือ ClassroomHomeroomTeacher ซึ่งเชื่อมห้องเรียนกับบุคลากร

ข้อมูลไหลเข้ามาที่จุดมอบตัว (กระบวนการ 3.0) โดยตอนนั้นระบบคัดลอกข้อมูลตัวบุคคล ที่อยู่ สุขภาพ และผู้ปกครองจากใบสมัครมาเป็นชุดของนักเรียน แล้วนักเรียนถูกจัดเข้าห้องเรียนที่สร้างไว้ตามปีและระดับชั้น (กระบวนการ 4.0) ผ่านตาราง StudentClassHistory ซึ่งเพิ่มแถวใหม่ทุกครั้งที่เปลี่ยนห้องหรือเลื่อนชั้น (กระบวนการ 5.0) เมื่อสถานะนักเรียนเปลี่ยน เช่น ลาออก จบ หรือย้าย ระบบเพิ่มแถวใน StudentStatusHistory (กระบวนการ 6.0) ส่วนครูประจำชั้นเชื่อมผ่าน ClassroomHomeroomTeacher (กระบวนการ 7.0) ค่าสถานะที่ใช้จริงของ `Student.status` ❓ ยังไม่พบรายการค่าในแหล่งข้อมูล

เหตุผลการออกแบบมี 4 ข้อ ข้อแรก ไม่มีตารางบุคคลกลาง (person) เพราะเมื่อใบสมัครเป็น log ตารางนี้จะเหลือแค่นักเรียนที่เกิดตอนมอบตัว ซึ่งซ้ำกับ Student ทุกประการ จึงให้ข้อมูลตัวบุคคลอยู่ที่ Student เอง และไม่รวมกับ Employees เพราะจะกระทบงานฝั่งบุคลากร (ADR 0002) ข้อสอง ข้อมูลของนักเรียนเป็นสำเนา ไม่ใช่การอ้างอิงถึงใบสมัคร จึงแก้ข้อมูลของนักเรียนได้โดยไม่แตะใบสมัคร ใบสมัครคงเป็นข้อมูล ณ วันสมัคร (ADR 0001) ข้อสาม ห้องเรียนของนักเรียนแยกเป็นตารางประวัติ StudentClassHistory แทนการเก็บห้องไว้ใน Student เพราะอาจารย์ทักว่าห้องควรเก็บเป็น log ทำให้ดูย้อนหลังได้ว่าเคยอยู่ห้องไหน ข้อสี่ ห้องหนึ่งมีครูประจำชั้นได้หลายคน และครูหนึ่งคนประจำได้ 1 ห้องต่อปี แบบเดิมที่เก็บครูไว้ในห้องช่องเดียวจึงผิดด้าน และต้องใช้ตารางคั่น ClassroomHomeroomTeacher (พร้อม `academicYearID`) แทน

ดูรูป ER A4 · ทะเบียนนักเรียน (1/2) และ (2/2) และพจนานุกรมข้อมูลของตารางในหมวดทะเบียนนักเรียน

## หมวดตั้งค่าโรงเรียนและตารางอ้างอิงกลาง

หมวดนี้เก็บค่าตั้งต้นที่ทุกหมวดอื่นต้องใช้ร่วมกัน ได้แก่ ข้อมูลโรงเรียน ปีการศึกษาและภาคเรียน ระดับชั้น แผนการเรียน อาคารและห้องจริง ตารางที่อยู่ของประเทศไทย รวมถึงค่าตั้งค่าของระบบ ใช้ให้เจ้าหน้าที่ตั้งค่าครั้งเดียวแล้วให้ทั้งฝั่งรับสมัครและทะเบียนนักเรียนอ้างถึง โดยไม่ต้องเก็บซ้ำ ระบบนี้ทำสำหรับโรงเรียนเดียว จึงไม่มีรหัสโรงเรียนในตารางอื่น

### ตารางในหมวดนี้ (ภาพรวมก่อนดูรูป ER)

| ชื่อตาราง | รายละเอียดตาราง |
|---|---|
| SchoolData | ข้อมูลโรงเรียน โรงเรียนเดียว มีแถวเดียว |
| Countries | ประเทศ ข้อมูลอ้างอิงสำหรับที่อยู่ |
| Provinces | จังหวัด ข้อมูลอ้างอิงสำหรับที่อยู่ |
| Districts | อำเภอ/เขต ข้อมูลอ้างอิงสำหรับที่อยู่ |
| SubDistricts | ตำบล/แขวง ใช้หาอำเภอ จังหวัด และรหัสไปรษณีย์ |
| AcademicYears | ปีการศึกษา ใช้ร่วมสองฝั่ง มีปีที่ใช้งานอยู่ปีเดียว |
| Semesters | ภาคเรียนของปีการศึกษา ภาคที่ 1 และ 2 ห้ามซ้ำในปีเดียวกัน |
| SchoolSchedule | เวลาเรียนรายภาคเรียน (เข้า-เลิก สาย ขาด กลับก่อน) เก็บย้อนหลังได้ |
| SchoolCalendar | ปฏิทินโรงเรียน เหตุการณ์ในปีการศึกษา |
| EducationStage | ช่วงชั้น เช่น มัธยมต้น มัธยมปลาย ใช้ร่วมระดับชั้นและแผนการเรียน |
| EducationLevels | ระดับชั้นแถวละชั้น ใช้ร่วมสองฝั่ง เลื่อนชั้นผ่านระดับชั้นถัดไป |
| StudyProgram | แผนการเรียนที่โรงเรียนเปิดสอน แถวเดียวถาวร |
| Building | อาคารของโรงเรียน ห้องกายภาพชี้มาที่อาคาร |
| SchoolRoom | ห้องกายภาพ เก็บชื่อ อาคาร ชั้น ความจุ และสเปกห้องสอบ |
| FieldDefinition | ตั้งค่าช่องในฟอร์ม (เปิด/ปิด บังคับกรอก ชื่อที่แสดง ลำดับ) ไม่ใช่ข้อมูลผู้สมัคร |
| StudentColumnSetting | ตั้งว่าหน้ารายชื่อนักเรียนโชว์คอลัมน์ไหน |
| EmailTemplate | แบบร่างอีเมลสำเร็จรูปสำหรับแจ้งผลผู้ปกครอง |
| SystemSetting | ค่าตั้งค่าระบบ เช่น รูปแบบรหัสนักเรียน |
| ActivityLog | ประวัติการทำรายการของเจ้าหน้าที่ |

ตารางจากหมวดอื่นที่เกี่ยวข้อง (ปรากฏเป็นกล่องเทาในรูป ER A4 · ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง)

| ชื่อตาราง | หมวดเจ้าของ | เกี่ยวข้องกับหมวดนี้อย่างไร |
|---|---|---|
| Address | บุคลากร | Address ชี้มาที่ SubDistricts และ Countries ผ่าน `subDistrictID` และ `countryID` เพื่อบอกตำบลและประเทศของที่อยู่บุคลากร |
| StudentAddress | ทะเบียนนักเรียน | StudentAddress ชี้มาที่ SubDistricts ผ่าน `subDistrictID` เพื่อบอกตำบลของที่อยู่นักเรียน |
| StudentDocument | ทะเบียนนักเรียน | StudentDocument ชี้มาที่ FieldDefinition ผ่าน `fieldID` เพื่อบอกชนิดเอกสาร |
| Classroom | ทะเบียนนักเรียน | Classroom ชี้มาที่ AcademicYears, EducationLevels, StudyProgram และ SchoolRoom เพื่อบอกปี ระดับชั้น แผนการเรียน และห้องจริงของห้องเรียน |
| ClassroomHomeroomTeacher | ทะเบียนนักเรียน | ClassroomHomeroomTeacher ชี้มาที่ AcademicYears ผ่าน `academicYearID` เพื่อบอกปีที่ครูประจำชั้น |
| ApplicantAddress | รับสมัคร | ApplicantAddress ชี้มาที่ SubDistricts ผ่าน `subDistrictID` เพื่อบอกตำบลของที่อยู่ผู้สมัคร |
| ApplicationDocument | รับสมัคร | ApplicationDocument ชี้มาที่ FieldDefinition ผ่าน `fieldID` เพื่อบอกชนิดเอกสาร |
| AdmissionRound | รับสมัคร | AdmissionRound ชี้มาที่ AcademicYears ผ่าน `academicYearID` เพื่อบอกปีการศึกษาของรอบ |
| AdmissionCoursePlan | รับสมัคร | AdmissionCoursePlan ชี้มาที่ StudyProgram ผ่าน `studyProgramID` เพื่อบอกแผนการเรียนที่เปิดรับ |

ตารางหลักที่ปรากฏใน DFD Level 1 มี 3 ตาราง AcademicYears คือปีการศึกษา มีปีที่ใช้งานอยู่ปีเดียว EducationLevels คือระดับชั้นแถวละชั้น (ม.1 ถึง ม.6 และเปิดให้เพิ่มประถมในอนาคต) แต่ละแถวชี้ระดับชั้นถัดไปด้วย `nextEducationLevelID` ถ้าว่างแปลว่าจบช่วงชั้น และ StudyProgram คือแผนการเรียนที่โรงเรียนเปิดสอน มีแถวเดียวถาวร ไม่เกิดใหม่ทุกปี ตารางที่เหลือมีหลายกลุ่ม กลุ่มเวลาและช่วงชั้น ได้แก่ Semesters SchoolSchedule SchoolCalendar และ EducationStage (ช่วงชั้น เช่น มัธยมต้น มัธยมปลาย) กลุ่มโรงเรียนและสถานที่ ได้แก่ SchoolData (แถวเดียว) Building และ SchoolRoom กลุ่มที่อยู่ 4 ตาราง ได้แก่ Countries Provinces Districts และ SubDistricts กลุ่มที่เหลือเป็นตั้งค่าการทำงานของระบบ ได้แก่ FieldDefinition StudentColumnSetting EmailTemplate SystemSetting และ ActivityLog

ข้อมูลของหมวดนี้เป็นต้นทางของเส้นหลายเส้นในภาพ AcademicYears และ StudyProgram ป้อนให้รอบรับสมัครและแผนที่เปิดรับ (กระบวนการ 1.0) ส่วน AcademicYears และ EducationLevels ป้อนให้การสร้างห้องเรียนรายปีใน Classroom (กระบวนการ 4.0) ตารางที่อยู่ 4 ตารางเรียงเป็นสายตั้งแต่ประเทศ จังหวัด อำเภอ จนถึงตำบล โดยที่อยู่ของผู้สมัคร นักเรียน บุคลากร และโรงเรียนชี้ที่ SubDistricts แล้วหาอำเภอ จังหวัด และรหัสไปรษณีย์ต่อจากตำบลได้เอง

เหตุผลการออกแบบมี 4 ข้อ ข้อแรก ระดับชั้นกับช่วงชั้นแยกเป็นสองตาราง เพราะ ม.1 เป็นระดับชั้น ส่วน ม.ต้น เป็นช่วงชั้นที่รวม ม.1 ถึง ม.3 การแยกเป็นตารางทำให้เพิ่มประถมได้โดยไม่ต้องแก้โครงสร้าง ข้อสอง ใช้ตาราง EducationLevels ตารางเดียวร่วมกันทั้งรับสมัคร ห้องเรียน และฝั่งบุคลากร ไม่แยกสำเนาของแต่ละฝั่ง ข้อสาม ปีการศึกษาเป็นของตารางส่วนกลางตารางเดียว ทั้งสองฝั่งชี้มาที่นี่ ข้อสี่ เวลาเรียนใน SchoolSchedule ผูกกับภาคเรียน จึงเปลี่ยนได้ทุกภาคและเก็บของเก่าไว้เช็กการมาสายย้อนหลังได้ ส่วน FieldDefinition เก็บเพียงการตั้งค่าช่องในฟอร์ม (เปิดหรือปิด บังคับกรอกหรือไม่ ชื่อที่แสดง ลำดับ) ไม่ใช่ข้อมูลผู้สมัคร คำตอบจริงอยู่ในคอลัมน์ของ Application และ Student ตาม `fieldKey` และ StudentColumnSetting ก็เก็บแค่ว่าหน้ารายชื่อนักเรียนโชว์คอลัมน์ไหน

ดูรูป ER A4 · ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง (1/3) (2/3) และ (3/3) และพจนานุกรมข้อมูลของตารางในหมวดนี้

## หมวดบุคลากร

หมวดนี้เก็บข้อมูลของบุคลากรและครู ใช้ให้ฝ่ายบุคคลบันทึกประวัติรายคน และเป็นต้นทางข้อมูลครูให้ฝั่งทะเบียนนักเรียนเลือกเป็นครูประจำชั้น โครงสร้างหมวดนี้มาจากฝั่งบุคลากร (Service B) ซึ่งยังไม่ได้ยืนยันกับเจ้าของข้อมูล ❓ ข้อความต่อไปนี้จึงอธิบายเท่าที่เห็นจากตารางเท่านั้น

### ตารางในหมวดนี้ (ภาพรวมก่อนดูรูป ER)

| ชื่อตาราง | รายละเอียดตาราง |
|---|---|
| Employees | ข้อมูลหลักของบุคลากรและครู เป็นตารางแม่ของตารางบุคลากรทุกตาราง |
| Education | ประวัติการศึกษาของบุคลากร 1 คนมีได้หลายแถว |
| RoyalDecorations | เครื่องราชอิสริยาภรณ์ที่บุคลากรได้รับ |
| License | ใบอนุญาตหรือใบประกอบวิชาชีพของบุคลากร |
| ToeicScore | ผลสอบ TOEIC ของบุคลากร |
| JobDetails | ข้อมูลการทำงานและตำแหน่งของบุคลากร |
| Training | ประวัติการอบรมและศึกษาดูงานของบุคลากร |
| FamilyMember | ข้อมูลสมาชิกครอบครัวของบุคลากร |
| Address | ที่อยู่บุคลากร 1 คนมีได้หลายที่อยู่ แยกประเภท |

โครงสร้างฝั่งบุคลากร (Service B) ยังไม่ได้ยืนยันกับเจ้าของข้อมูล ❓ รายละเอียดข้างต้นอ้างจากข้อมูลที่เห็นในตารางเท่านั้น

ตารางจากหมวดอื่นที่เกี่ยวข้อง (ปรากฏเป็นกล่องเทาในรูป ER A4 · บุคลากร)

| ชื่อตาราง | หมวดเจ้าของ | เกี่ยวข้องกับหมวดนี้อย่างไร |
|---|---|---|
| ClassroomHomeroomTeacher | ทะเบียนนักเรียน | ClassroomHomeroomTeacher ชี้มาที่ Employees ผ่าน `employeeID` เพื่อเลือกบุคลากรเป็นครูประจำชั้น |
| Department | ตั้งค่าบุคลากร | Department ชี้มาที่ Employees ผ่าน `headEmployeeID` เพื่อบอกหัวหน้าแผนก (ว่างได้) และ JobDetails ชี้ไปที่ Department ผ่าน `departmentID` |

| StaffType | ตั้งค่าบุคลากร | JobDetails ชี้ไปที่ StaffType ผ่าน `staffTypeID` เพื่อบอกประเภทบุคลากร |
| Position | ตั้งค่าบุคลากร | JobDetails ชี้ไปที่ Position ผ่าน `positionID` เพื่อบอกตำแหน่ง |
| SubDistricts | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | Address ชี้ไปที่ SubDistricts ผ่าน `subDistrictID` เพื่อบอกตำบลของที่อยู่บุคลากร |
| Countries | ตั้งค่าโรงเรียนและตารางอ้างอิงกลาง | Address ชี้ไปที่ Countries ผ่าน `countryID` เพื่อบอกประเทศของที่อยู่บุคลากร |

ตารางหลักคือ Employees ข้อมูลหลักของบุคลากรและครู เป็นตารางแม่ของตารางบุคลากรทุกตาราง เก็บชื่อ คำนำหน้า เลขบัตรประชาชนหรือเลขหนังสือเดินทาง วันเกิด และบทบาท ตารางที่เหลือเป็นตารางย่อยที่ชี้กลับมาที่ `employeeID` ได้แก่ Education (ประวัติการศึกษา) RoyalDecorations (เครื่องราชอิสริยาภรณ์) License (ใบอนุญาตหรือใบประกอบวิชาชีพ) ToeicScore (ผลสอบ TOEIC) JobDetails (ข้อมูลการทำงานและตำแหน่ง) Training (ประวัติการอบรม) FamilyMember (สมาชิกครอบครัว) และ Address (ที่อยู่) บุคลากรหนึ่งคนมีได้หลายแถวในแต่ละตารางย่อย

ข้อมูลไหลออกจากหมวดนี้สองทาง ทางแรกไปที่ห้องเรียน ตาราง ClassroomHomeroomTeacher ใช้ `employeeID` เลือกบุคลากรเป็นครูประจำชั้น (กระบวนการ 7.0 ส่วน "กำหนดครูประจำชั้น") ทางที่สองไปที่บัญชีผู้ใช้ ตาราง User ชี้ที่ Employees และบุคลากรหนึ่งคนมีบัญชีได้หนึ่งบัญชี (กระบวนการ 7.0 ส่วน "บัญชีเข้าระบบ") ใครเป็นผู้สร้างแถวใน Employees และสร้างตอนไหน ❓ แหล่งข้อมูลยังไม่ระบุ

เหตุผลการออกแบบที่ยืนยันได้มี 2 ข้อ ข้อแรก Employees เก็บข้อมูลตัวบุคคลของบุคลากรไว้เอง และไม่รวมกับ Student เพราะการรวมเป็นตารางบุคคลกลางจะกระทบงานฝั่งบุคลากร จึงเลือกไม่รวม (ADR 0002) ข้อสอง ที่อยู่ของบุคลากรรองรับครูต่างชาติ โดยตำบลว่างได้ และใช้ `addressLine` เก็บที่อยู่เต็มแทนสำหรับที่อยู่ต่างประเทศ กติกาคือต้องมีตำบลหรือที่อยู่เต็มอย่างน้อยหนึ่งช่อง ส่วน `idType` ใน Employees แยกบัตรประชาชนออกจากหนังสือเดินทางด้วยเหตุผลเดียวกัน

ดูรูป ER A4 · บุคลากร (1/2) และ (2/2) และพจนานุกรมข้อมูลของตารางในหมวดบุคลากร

## หมวดตั้งค่าบุคลากร

หมวดนี้เก็บค่าตั้งต้นที่ใช้จัดการบุคลากร ได้แก่ ประเภทบุคลากร ตำแหน่ง แผนก เวลาทำงาน กะพิเศษ บัญชีผู้ใช้และสิทธิ์ และผู้ลงนามในเอกสาร ใช้ให้ผู้ดูแลระบบตั้งค่าในหน้าตั้งค่าบุคลากร ตารางกลุ่มนี้เป็นร่างที่ยังรอตรวจ ❓

### ตารางในหมวดนี้ (ภาพรวมก่อนดูรูป ER)

| ชื่อตาราง | รายละเอียดตาราง |
|---|---|
| StaffType | ประเภทบุคลากร เช่น ข้าราชการครู ครูอัตราจ้าง ผู้บริหาร เจ้าหน้าที่ |
| Position | ตำแหน่ง เช่น ครูผู้ช่วย ครูชำนาญการ ผู้อำนวยการ |
| PositionStaffType | ตารางคั่นที่ให้ตำแหน่งหนึ่งอยู่ได้หลายประเภทบุคลากร |
| Department | แผนกหรือกลุ่มสาระการเรียนรู้ มีหัวหน้าได้ (ไม่บังคับ) |
| StaffWorkTime | เวลาทำงานปกติของบุคลากร ทั้งโรงเรียนมีแถวเดียว |
| Shift | กะพิเศษ เช่น เวรรถโรงเรียน เวรกลางคืน |
| User | ผู้ใช้งานระบบ 1 บุคลากรมีได้ 1 บัญชี |
| Permission | สิทธิ์การใช้งานแต่ละอย่าง (6 รายการ) |
| UserPermission | สิทธิ์รายบุคคลของผู้ใช้ 1 แถวต่อการให้สิทธิ์ 1 อย่าง |
| Signatory | ผู้ลงนามในเอกสาร ผูกกับบุคลากรได้ (ว่าง = บุคคลภายนอก) |
| DocSignatory | เอกสารชนิดไหนให้ใครลงนามได้ หนึ่งชนิดมีได้หลายคน |

ตารางกลุ่มนี้เป็นร่างที่ยังรอตรวจ ❓

ตารางจากหมวดอื่นที่เกี่ยวข้อง (ปรากฏเป็นกล่องเทาในรูป ER A4 · ตั้งค่าบุคลากร)

| ชื่อตาราง | หมวดเจ้าของ | เกี่ยวข้องกับหมวดนี้อย่างไร |
|---|---|---|
| JobDetails | บุคลากร | JobDetails ชี้ไปที่ StaffType, Position และ Department ผ่าน `staffTypeID` `positionID` `departmentID` เพื่อบอกประเภท ตำแหน่ง และแผนกของบุคลากร |
| Employees | บุคลากร | Department, User และ Signatory ชี้มาที่ Employees ผ่าน `headEmployeeID` `employeeID` `employeeID` ตามลำดับ |

ตารางหลักคือ User และ Employees (ซึ่งอยู่ใน DFD Level 1) ที่เชื่อมกันเป็นบัญชีเข้าระบบ User เก็บ `accessRole` (ผู้อำนวยการ รองผู้อำนวยการ ผู้ดูแลระบบ หรือครู) และสถานะใช้งาน ชื่อและตำแหน่งไม่เก็บซ้ำ ดึงจาก Employees ตารางที่เหลือแบ่งเป็น 4 กลุ่ม กลุ่มโครงสร้างองค์กร ได้แก่ StaffType (เช่น ข้าราชการครู ครูอัตราจ้าง) Position (เช่น ครูผู้ช่วย ผู้อำนวยการ) PositionStaffType (ตำแหน่งหนึ่งอยู่ได้หลายประเภท) และ Department (แผนกหรือกลุ่มสาระ มีหัวหน้าได้โดยไม่บังคับ) กลุ่มเวลา ได้แก่ StaffWorkTime (เวลาทำงานปกติ ทั้งโรงเรียนมีแถวเดียว) และ Shift (กะพิเศษ เช่น เวรรถโรงเรียน) กลุ่มสิทธิ์ ได้แก่ Permission (สิทธิ์การใช้งาน 6 รายการ) และ UserPermission (สิทธิ์รายบุคคล 1 แถวต่อ 1 สิทธิ์) และกลุ่มผู้ลงนาม ได้แก่ Signatory และ DocSignatory (เอกสารชนิดใดให้ใครลงนามได้)

ข้อมูลไหลจาก Employees ไปที่ User ตามกระบวนการ 7.0 "บัญชีเข้าระบบ" ส่วน JobDetails ของหมวดบุคลากรชี้มาที่ StaffType Position และ Department เพื่อบอกว่าบุคลากรคนนั้นมีตำแหน่ง ประเภท และแผนกใด Department ชี้กลับไปที่ Employees ผ่าน `headEmployeeID` และ Signatory ชี้ที่ Employees ได้ ถ้าว่างแปลว่าเป็นบุคคลภายนอก ส่วนรายละเอียดว่าใครเป็นผู้ตั้งค่า และขั้นตอนใช้งานจริง ❓ ยังไม่ยืนยัน

เหตุผลการออกแบบที่มีในแหล่งข้อมูลมีดังนี้ ใช้ตารางคั่น PositionStaffType เพราะตำแหน่งหนึ่งอยู่ได้หลายประเภท ตารางบทบาทกับสิทธิ์เขียนไว้ในโค้ดโดยไม่สร้างตารางในฐานข้อมูล จึงมีเพียง Permission กับ UserPermission สำหรับสิทธิ์รายบุคคล วันหยุดไม่สร้างตารางแยก ใช้ SchoolCalendar โดยให้ประเภทเหตุการณ์เป็นวันหยุดแทน และ `docType` ใน DocSignatory เก็บเป็นข้อความ เพราะรายการชนิดเอกสารยังมีสองชุดที่ไม่ตรงกัน ❓

ดูรูป ER A4 · ตั้งค่าบุคลากร และพจนานุกรมข้อมูลของตารางในหมวดตั้งค่าบุคลากร
