## กฎเหล็ก: Opus วางแผน → Sonnet ลงมือเสมอ

เหตุผล: Opus แพงกว่า Sonnet มาก งานที่ให้ Opus ลงมือแก้โค้ดเองทั้งหมดจะแพงกว่าการแบ่งงานเป็น
"Opus คิด/วางแผน" + "Sonnet เขียนโค้ดตามแพลน" อย่างชัดเจน — แต่การแบ่งงานจะได้ผลจริงก็ต่อเมื่อ
แพลนละเอียดพอที่ Sonnet ทำตามได้โดยไม่ต้องตัดสินใจเชิงออกแบบเอง (เพราะ Sonnet ไม่เห็นบทสนทนา
ก่อนหน้า ไม่มี context เดียวกับ Opus)

**เมื่อทำงานในโปรเจกต์นี้ (หรือโปรเจกต์ไหนก็ตามที่ noeysod สั่งงาน):**

1. **Opus (session หลัก) ทำหน้าที่วางแผนเท่านั้น**: สำรวจโค้ดเท่าที่จำเป็นต่อการตัดสินใจ
   (ใช้ Grep/Glob/อ่านเฉพาะช่วงที่เกี่ยวข้อง — ไม่อ่านทั้งไฟล์ถ้าไม่จำเป็น), ตัดสินใจเชิงออกแบบ/
   สถาปัตยกรรม, เขียนแพลนละเอียด, และตรวจงานรอบสุดท้ายหลัง Sonnet ทำเสร็จ (git diff แบบย่อ พอ
   ยืนยันว่าตรงแพลน ไม่ต้อง re-read ทุกไฟล์)
2. **ห้าม Opus แก้โค้ด/สร้างไฟล์เองโดยตรง** — งานลงมือทั้งหมดต้องส่งผ่าน `Agent` tool ด้วย
   `model: "sonnet"` เสมอ ยกเว้นกรณีเดียว: งานเล็กมาก (เช่น แก้ 1-2 บรรทัด, พิมพ์ผิด) ที่การเขียน
   แพลนแล้ว spawn subagent จะแพง/ช้ากว่าการแก้เองตรง ๆ อย่างชัดเจน — กรณีนี้ Opus แก้เองได้ทันที
   โดยไม่ต้องขออนุญาต แต่ให้บอกผู้ใช้สั้น ๆ ว่าทำไมถึงข้ามการ spawn subagent
3. **ต้องประหยัดกว่าการให้ Opus ทำเองทั้งหมดจริง ๆ** ไม่ใช่แค่ทำตามรูปแบบ — ถ้าแพลนซับซ้อนจน
   ต้องมี back-and-forth หลายรอบกับ Sonnet (ซึ่งกินเวลา Opus ไปกับการตรวจ/แก้แพลนซ้ำ) ให้ทบทวนว่า
   งานนี้ควรแตกเป็นแพลนย่อยที่ชัดกว่านี้หรือไม่ แทนที่จะปล่อยให้วนซ้ำ

## มาตรฐานแพลนที่ Sonnet ทำตามได้โดยไม่ต้องคิดเอง

ทุกแพลนที่ Opus เขียนแล้วจะส่งให้ Sonnet subagent ต้องมีองค์ประกอบนี้ครบ:

- **เป้าหมาย** 1–2 บรรทัด + ขอบเขตที่ "ห้ามแตะ" (เช่น อย่าแก้ระบบอื่นที่ไม่เกี่ยวข้อง)
- **path ไฟล์แบบเต็ม** (ไม่ใช่ path ย่อ) พร้อม**ชื่อฟังก์ชัน/selector/ข้อความ anchor**ที่ใช้หา
  จุดแก้ในไฟล์ — ห้ามอ้างอิงแค่เลขบรรทัด (เลขบรรทัดเปลี่ยนได้เสมอ)
- **ขั้นตอนเรียงลำดับ** แต่ละขั้นระบุชัดว่า "แก้อะไร → เปลี่ยนเป็นอะไร" ใส่ code snippet ตัวอย่าง
  ในจุดที่กำกวมหรือมีรายละเอียดเฉพาะ (syntax, ชื่อ property, ตำแหน่งใน object) ไม่ปล่อยให้ Sonnet
  ต้องเดาการออกแบบเอง
- **กฎของโปรเจกต์ที่เกี่ยวข้องกับงานนั้น** — สรุปมาให้ในแพลนเลย (Sonnet subagent อาจไม่ได้อ่าน
  `CLAUDE.md`/`AGENTS.md` ของโปรเจกต์นั้นเองถ้าไม่บอกให้อ่าน) เช่นตัวอย่างในโปรเจกต์นี้:
  - แก้/เพิ่ม/ลบเมนูใด ๆ ต้องแก้ `NAV_GROUPS` ใน `shared/cross-nav.js` เสมอ
  - ห้ามใช้ class `submenu-item` กับเมนูย่อยที่ลิงก์ข้ามหน้า (ใช้ `submenu-link` แทน)
  - `schooldark/` กับ `admission/` ใช้ design system คนละชุด ห้ามแปลงฝั่งใดไปหาอีกฝั่ง
- **วิธีตรวจว่าเสร็จ**: เปิดไฟล์ไหนผ่าน `file:///`, ต้องเห็นผลอะไร, หรือคำสั่ง grep/build ที่ใช้ยืนยัน
- **การแบ่งงาน**: ถ้างานแตกเป็นก้อนอิสระจากกันได้ ให้ระบุไว้ชัดว่าก้อนไหนอิสระ (ส่ง Sonnet หลายตัว
  พร้อมกันได้) ก้อนไหนต้องรอผลก้อนก่อนหน้า (ส่งตามลำดับ)

## ขั้นตอนทำงานต่อ 1 งาน

1. Opus สำรวจ + วางแผนตามมาตรฐานข้างต้น
2. ถ้าแพลนเปลี่ยนแปลงเยอะ/เสี่ยง ให้ผู้ใช้ (noeysod) อนุมัติก่อน
3. ส่งแพลนแบบเต็มใน prompt ให้ Sonnet subagent ผ่าน `Agent` tool (`model: "sonnet"`) —
   ห้ามส่งแค่สรุปสั้น ๆ เพราะ subagent ไม่เห็นบทสนทนาที่ผ่านมา
4. Opus ตรวจผลแบบย่อ (`git diff`, grep จุดสำคัญ) — ไม่ใช่ re-review ทั้งไฟล์ใหม่ทั้งหมด
5. รายงานผู้ใช้สั้น กระชับ ตรงประเด็น
6. ถ้า Sonnet ทำพลาด: ส่งกลับไปให้ Sonnet แก้เอง พร้อมชี้จุดผิดให้ชัด — **ห้าม Opus แก้เอง**
   (ยกเว้นเข้าเงื่อนไขข้อยกเว้นงานจิ๊บจิ๋วด้านบน)

## เอกสารของ noeysod อยู่ที่ไหน

บันทึก/ความรู้ใหม่ที่ได้จากงานของ noeysod (สถานะงาน, การตัดสินใจที่ไม่โผล่ในโค้ด, ความชอบด้าน UI ฯลฯ)
ให้เขียนต่อท้ายไฟล์นี้ (`uxui-merged/noeysod.md`) — **ไม่ใช่** `CLAUDE.md` (ไฟล์กลางของทีม ตามกฎ
ด้านบนของไฟล์นี้อยู่แล้ว)

ของที่เคยเขียนไว้ใน `parent/CLAUDE.md` ก่อนกฎนี้ (รายละเอียดเชิงเทคนิคของพอร์ทัลผู้ปกครอง: รายการ
หน้า, โครง Nav, โครง Data) **ไม่ต้องย้อนไปแก้/ย้าย** — ยังถูกต้องและใช้อ้างอิงต่อไปได้ตามปกติ
เพียงแต่ตั้งแต่นี้ไป ให้บันทึกของใหม่ที่นี่แทน

## ความชอบด้าน UI ของ noeysod

- ชอบหน้าแรกกะทัดรัด ไม่ชอบกล่องสรุปข้อมูลเล็ก ๆ ที่แยกเป็นกล่องใหญ่โต ๆ จนดู "ขาด ๆ เกิน ๆ" —
  ถ้าเป็นข้อมูลที่เกี่ยวกันอยู่แล้ว (เช่น ของเด็กคนเดียวกัน) ให้ยุบไปรวมในการ์ดที่เกี่ยวข้องแทน
- ไม่ชอบองค์ประกอบซ้ำซ้อนกับสิ่งที่มีอยู่แล้ว เช่น หลอด progress ที่บอกข้อมูลซ้ำกับตัวเลขข้าง ๆ —
  ให้ใช้สี/ขนาดตัวอักษรสื่อสถานะแทนเมื่อพื้นที่จำกัด
- ไม่ชอบลิงก์ซ้ำหลายจุดที่พาไปที่เดียวกัน (เช่น รูป+ชื่อ+ปุ่ม "ดูเพิ่ม" ทั้ง 3 อันลิงก์เดียวกัน) —
  ให้รวมเป็น stretched link (การ์ดทั้งใบกดได้/hover ได้) แทน แล้วเก็บลิงก์ย่อยไว้เฉพาะจุดที่ปลายทาง
  ต่างกันจริง ๆ
- ตัวเลข/การ์ดสรุปบนหน้าแรกควร "กดแล้วพาไปหน้าเต็ม" ของเรื่องนั้นเสมอ ไม่ใช่แค่โชว์ตัวเลขเฉย ๆ
- ของที่เป็นเรื่องเดียวกันแต่แยกเป็นหลายเมนู/หลายรายการ ให้เสนอรวมเป็นอันเดียวก่อน (เช่น SDQ
  ฉบับผู้ปกครอง/นักเรียน 2 เมนู → รวมเป็นเมนูเดียว)
- ยินดีให้ลองทำไปก่อนได้เลยโดยไม่ต้องถามเยอะ ถ้าผลออกมาไม่สวย/ไม่ตรงใจจะบอกให้แก้กลับเอง
- กลุ่มปุ่ม/ทางลัดต้องมีป้ายบอกหมวดชัดเจน (เช่น "เมนูลัด") และควรอยู่ในกล่อง — ปุ่มลอยแบบ
  แคปซูล `rounded-full` ไม่มีหัวข้อกำกับ จะดูเหมือน chip/ตัวกรอง ไม่ใช่เมนู
