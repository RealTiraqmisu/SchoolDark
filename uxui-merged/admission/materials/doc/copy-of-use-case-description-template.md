# Use Case Description — Template

> โครงมาตรฐานที่ใช้กับทุก Use Case ของโปรเจกต์นี้ เอกสารจริงอยู่ที่ `use-case-description-index.md`
> และไฟล์ `uc-*.md` ในโฟลเดอร์เดียวกัน — ทุก Use Case เขียนเป็นตาราง 2 คอลัมน์ 12 แถวตามโครงด้านล่าง
> เพื่อให้คัดลอกไปวางในเอกสาร Word ได้โดยตรง

## โครงตารางเปล่า

```markdown
## UC-XXX-NN [ชื่อ Use Case]

| หัวข้อ | รายละเอียด |
|---|---|
| **Use Case Name** | [ชื่อ Use Case ด้วยรูปแบบ Verb-Noun เช่น ยื่นใบสมัครเรียนออนไลน์] |
| **ID** | [รหัสอ้างอิง เช่น UC-APP-01] |
| **Scenario** | [สถานการณ์ตัวอย่างที่ทำให้ต้องใช้ Use Case นี้ เขียนเป็นเรื่องเล่าสั้นๆ] |
| **Trigger Event** | [เหตุการณ์ที่จุดชนวนให้ Use Case เริ่มทำงาน] |
| **Brief Description** | [ภาพรวมสั้นๆ ว่า Use Case นี้ทำอะไร เพื่อบรรลุเป้าหมายใด] |

| **Stakeholders** | [ผู้มีส่วนได้ส่วนเสียที่ไม่ได้ลงมือใช้ระบบเอง แต่สนใจผลลัพธ์] |

| **Alternate/Exception Flows** | **Alt Flow Na — ชื่อกรณี:** [ทางเลือกที่ยังทำให้ Use Case สำเร็จได้]<br><br>**Exception Na — ชื่อกรณี:** [ข้อผิดพลาดที่ทำให้ Use Case ไม่สำเร็จ และระบบตอบสนองอย่างไร] |
```

## กติกาการเขียน

1. เขียนเป็นภาษาไทยในระดับการวิเคราะห์ความต้องการ (analysis level) — บอกว่า *ระบบทำอะไร*
   ไม่ใช่ *หน้าจอมีหน้าตาอย่างไร*
2. ห้ามอ้างถึงชื่อไฟล์ ชื่อฟังก์ชัน ชื่อตารางหรือคีย์ในฐานข้อมูล หรือคำเรียกส่วนประกอบหน้าจอ
   (หน้าต่าง ปุ่ม ช่องติ๊ก แท็บ สวิตช์ ไอคอน สี) — สิ่งเหล่านี้เป็นรายละเอียดของบทผลการพัฒนา ไม่ใช่ของ Use Case
3. ระบุ Actor ด้วยตำแหน่งงาน เช่น เจ้าหน้าที่ทะเบียน ผู้ดูแลระบบ ครูประจำชั้น ผู้สมัคร
   ไม่ใช้คำว่า "ผู้ใช้" ลอยๆ
4. Basic Flow ควรอยู่ที่ 6–10 ขั้นตอน รวบรายชื่อฟิลด์ข้อมูลเป็นกลุ่มแทนการแจกแจงทีละช่อง
   ส่วนรายชื่อฟิลด์แบบละเอียดให้ไปอยู่ใน Data Dictionary
5. Alternate Flow และ Exception Flow อย่างละไม่เกิน 4 ข้อ — ยุบกรณีที่มีสาเหตุเดียวกันเข้าด้วยกัน
6. 1 Use Case ตอบโจทย์ 1 Goal ของ 1 Primary Actor — ถ้ามีสอง Actor คนละกลุ่มทำคนละเป้าหมาย
   ให้แยกเป็นคนละ Use Case
7. ในเซลล์ตาราง ใช้ `<br>` แทนการขึ้นบรรทัดใหม่เสมอ และห้ามใช้อักขระ `|` ในเนื้อหา
   (เพื่อไม่ให้ตารางเสียรูปเมื่อคัดลอกไปวางใน Word)
